Security Architecture

The 4 Security Pillars

Defensive architecture built into Terraform from the very first line of code.

1. Zero-Trust Remote State

Encrypted at rest + Concurrency lock

Terraform state contains sensitive resource metadata and generated attributes. State is strictly locked in S3 with AWS KMS server-side encryption and DynamoDB distributed locking to prevent split-brain collisions.

kms_key_id = "alias/terraform-state-key"
dynamodb_table = "terraform-locks"

2. Secretless CI/CD via OIDC

Zero long-lived AWS Access Keys

Eliminates static AWS_ACCESS_KEY_ID credentials. GitHub Actions requests short-lived STS tokens directly using OpenID Connect (id-token: write) assuming a pre-configured IAM role.

role-to-assume: arn:aws:iam::*:role/github-oidc-terraform

3. Hardened Compute & IMDSv2

Protection against SSRF & unencrypted EBS

EC2 instances strictly enforce Instance Metadata Service v2 (http_tokens = "required") blocking common SSRF credential theft vulnerabilities. Root volumes use encrypted GP3 storage.

metadata_options { http_tokens = "required" }

4. Policy-as-Code Guardrails

Checkov & tfsec enforcement in PRs

Automated scans execute in GitHub Actions prior to terraform plan. Pull requests fail automatically if S3 encryption (CKV_AWS_19) or versioning is violated.

check: [ CKV_AWS_19, CKV_AWS_21, CKV_AWS_144 ]
